# Sentry — Explainable Fraud Detection for Job Postings

A full-stack ML/NLP system that classifies job postings as **Genuine** or
**Fraudulent**, explains each prediction with SHAP, compares six trained
models, and keeps a persistent history of every check.

Built against the PRD and Review 2 documents for this project (team:
Subash Venkat, Shivansh Ranjan). See `docs/PROJECT_NOTES.md` for how this
implementation maps to those documents and what to be aware of before you
present or submit it.

## What's inside

```
project/
├── data/fake_job_postings.csv      real EMSCAD-based dataset, ~17,880 rows
├── ml/train.py                     full training pipeline (see below)
├── backend/                        FastAPI app + trained model artifacts
├── frontend/                       React dashboard
├── docs/eda_plots/                 PNG plots generated by the training run
├── docker-compose.yml              runs the whole stack with one command
└── scripts/smoke_test.sh           end-to-end API test
```

The model artifacts in `backend/models/` are **already trained** — you do
not have to run the training pipeline to use the app. Re-run it only if you
want to reproduce the training from scratch or change the pipeline.

## Part 1 — Run everything with Docker (easiest)

If you have Docker Desktop installed, this is the fastest path and matches
the PRD's stack exactly (PostgreSQL, FastAPI, React).

1. Install Docker Desktop if you don't have it: https://www.docker.com/products/docker-desktop/
2. Open a terminal in the `project/` folder.
3. Run:
   ```
   docker compose up --build
   ```
4. Wait for it to say the backend and frontend are up (first build takes a
   few minutes; it's downloading Python/Node images and installing
   packages).
5. Open **http://localhost:3010** in your browser. That's the app.
6. The API alone is at **http://localhost:8010** — visit
   **http://localhost:8010/docs** for the interactive API reference
   (Swagger UI), which lets you try every endpoint by hand.
7. To stop everything: press `Ctrl+C`, then run `docker compose down`
   (add `-v` if you also want to delete the Postgres data volume).

Note: these ports (3010, 8010, 5433 for Postgres) are deliberately
non-default, since 3000/8000/5432 are common ports that other things on
your machine (a local Postgres install, another dev server, etc.) may
already be using. If any of these three still clash with something on
your machine, open `docker-compose.yml` and change the number on the left
of the colon in that service's `ports:` line — the number on the right
must stay the same, since that's the port used *inside* the container
network.

That's it — skip to **Part 3 (Testing it end to end)** below.

## Part 2 — Run it manually, without Docker

Use this if you don't have Docker, or if you want to modify and re-run
individual pieces (e.g. retrain a model).

### Prerequisites

- Python 3.10 or newer
- Node.js 18 or newer
- (Optional) PostgreSQL, if you don't want to use the default SQLite file

Check what you have:
```
python3 --version
node --version
npm --version
```

### 2.1 Backend

Open a terminal in `project/backend/`.

1. Create and activate a virtual environment (keeps these packages separate
   from anything else on your machine):
   ```
   python3 -m venv venv
   source venv/bin/activate        # on Windows: venv\Scripts\activate
   ```
2. Install the Python dependencies:
   ```
   pip install -r requirements.txt
   ```
3. Download the NLTK data used for text cleaning (stopwords, lemmatizer).
   This only needs to run once:
   ```
   python -m nltk.downloader stopwords wordnet omw-1.4
   ```
4. Start the API server:
   ```
   uvicorn app.main:app --reload --port 8000
   ```
   You should see `Application startup complete.` and
   `Uvicorn running on http://0.0.0.0:8000`.

   By default this uses a local SQLite file (`backend/predictions.db`) for
   prediction history — no database setup needed. If you want PostgreSQL
   instead, set an environment variable before starting:
   ```
   export DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/fraud_detection"
   ```
   (Create that database and user in Postgres first, and make sure
   `psycopg2-binary` — already in requirements.txt — is installed.)

5. Leave this terminal running. Open **http://localhost:8000/docs** in a
   browser to confirm the API is up and to explore it interactively.

### 2.2 Frontend

Open a **second** terminal in `project/frontend/` (leave the backend
running in the first one).

1. Install dependencies:
   ```
   npm install
   ```
2. Start the dev server:
   ```
   npm run dev
   ```
3. Open **http://localhost:5173** in your browser. The dev server is
   configured to forward any `/api/...` request to the backend on port
   8000 automatically, so both must be running at the same time.

## Part 3 — Testing it end to end

### 3.1 Through the browser (what a user would do)

1. Go to the app (**http://localhost:3010** for Docker, or
   **http://localhost:5173** for the manual setup).
2. On the **Submit a Posting** page, click **"Load suspicious sample"** to
   auto-fill a fake work-from-home scam posting, then click **"Check this
   posting."** You should see a verdict card (it should say
   **Fraudulent**), a confidence percentage, and a list of the words and
   fields ("factors") that pushed the model toward that decision.
3. Clear the form and fill in a realistic, boring job posting (e.g. copy a
   real listing from LinkedIn) and check it again — it should come back
   **Genuine** with high confidence.
4. Click **Model Comparison** in the sidebar. You'll see a metrics table
   for all six models (Dummy, Logistic Regression, Naive Bayes, Decision
   Tree, Random Forest, XGBoost), ROC curves overlaid, and a confusion
   matrix you can switch between models.
5. Click **Prediction History** — both postings you just checked should be
   listed with timestamps. Click a row to expand and see its top factors
   again.
6. Click **Dataset & EDA** — you'll see dataset-wide statistics: class
   balance, missing-value rates, industry distribution, fraud rate by
   whether a salary was listed, and the most common words in fraudulent
   postings.

If every one of those steps works, the system is functioning end to end.

### 3.2 Through the API directly (for verifying the backend on its own)

With the backend running, from `project/`:
```
./scripts/smoke_test.sh
```
This calls every endpoint in sequence (health check, list models, two
predictions, model comparison, EDA summary, history) and pretty-prints the
JSON responses. If any step fails, `curl`'s `-f` flag makes the script stop
and tell you which call failed.

Defaults to `http://localhost:8000`, which is correct for the manual
setup. If you're running via Docker (where the backend is on port 8010),
pass that instead: `./scripts/smoke_test.sh http://localhost:8010`

You can also just open **http://localhost:8000/docs** (or
**http://localhost:8010/docs** under Docker) and click "Try it out" on any
endpoint — this is the same Swagger UI FastAPI generates automatically
from the code, useful for demoing the API specifically.

## Part 4 — Re-running the ML training pipeline (optional)

The trained models, metrics, SHAP explainer, and EDA plots are already
checked into `backend/models/` and `docs/eda_plots/`. You only need to
redo this if you change the pipeline (e.g. try a different feature set) or
want to reproduce the results yourself.

From `project/`, with the backend's virtual environment active
(`source backend/venv/bin/activate`) and its dependencies installed:

```
python ml/train.py
```

This will:
1. Load `data/fake_job_postings.csv` and clean it.
2. Regenerate the EDA plots into `docs/eda_plots/`.
3. Re-run text preprocessing (lowercasing, HTML stripping, tokenizing,
   stop-word removal, lemmatization).
4. Rebuild TF-IDF + n-gram features and encode the structured fields.
5. Retrain all six models and re-evaluate them.
6. Refit the SHAP explainer on whichever model wins on F1 score.
7. Overwrite the artifacts in `backend/models/`.

It takes 2–5 minutes on a laptop CPU. Restart the backend afterward
(`uvicorn` picks up new model files only on startup, not automatically).

## Notes on what's simplified vs. the original PRD

Being direct about where this implementation differs from the PRD/Review
documents, so it doesn't surprise anyone during a review:

- **Database**: defaults to SQLite for zero-setup local development. Set
  `DATABASE_URL` (or use `docker compose`, which wires up real Postgres)
  to match the PRD's PostgreSQL requirement exactly.
- **SHAP explanations at prediction time**: the pre-fit `shap_explainer.joblib`
  is trained during the pipeline run, but the live `/predict` endpoint
  computes a fresh `TreeExplainer` per request for whichever tree-based
  model is selected (fast, since it's one row) rather than reusing the
  saved explainer object directly. For Logistic Regression it falls back
  to coefficient × feature-value; for Naive Bayes/Dummy the "factors" are a
  rougher proxy, not true SHAP values — flagged in the UI copy as such.
- **Dataset size**: the real ~17,880-row EMSCAD-derived dataset is used
  (not a subsample), matching the PRD.
- **Docker**: included and wired to Postgres as specified, but not
  something you're required to use — the manual setup path is fully
  supported too.
